# 条件变量

## `unique_lock` 最重要的场景：`condition_variable`

这也是为什么数据库、线程池代码中经常看到：

```cpp
std::unique_lock<std::mutex> lock(mutex_);
cv_.wait(lock);
```

很多初学者第一次看到都会奇怪：

> 为什么 `wait()` 要传一个 `unique_lock`？

因为等待条件变量时，有一个很重要的动作：

```text
先 unlock mutex
      ↓
线程睡眠
      ↓
有人 notify
      ↓
线程醒来
      ↓
重新 lock mutex
```

比如生产者消费者：

```cpp
std::mutex mutex;
std::condition_variable cv;
std::queue<int> queue;
```

消费者：

```cpp
void Consumer() {
    std::unique_lock<std::mutex> lock(mutex);

    cv.wait(lock, [] {
        return !queue.empty();
    });

    int value = queue.front();
    queue.pop();
}
```

重点看：

```cpp
cv.wait(lock, ...);
```

内部逻辑大概是：

```text
Consumer:

mutex 已锁
   ↓
发现 queue empty
   ↓
unlock mutex
   ↓
sleep
```

为什么必须 unlock？

因为生产者需要：

```cpp
lock mutex
queue.push(...)
unlock mutex
notify
```

如果 Consumer 睡觉的时候还拿着 mutex：

```text
Consumer:
持有 mutex
↓
睡眠

Producer:
需要 mutex
↓
拿不到
↓
无法 push

Consumer:
等 producer push
```

直接死锁。

所以 `condition_variable::wait()` 必须能够：

```text
unlock
sleep
wake
lock
```

而 `lock_guard` 不支持手动：

```cpp
unlock()
lock()
```

所以不能满足这个需求。

`unique_lock` 可以。

---

## 把 `wait()` 展开理解

这段：

```cpp
cv.wait(lock, [] {
    return !queue.empty();
});
```

可以粗略脑补成：

```cpp
while (queue.empty()) {
    lock.unlock();

    // 睡眠等待 notify
    sleep();

    lock.lock();
}
```

真实实现更复杂，并且“释放锁 + 睡眠”需要原子地配合完成，但作为理解模型这样看就够了。

因此：

```text
condition_variable
       ↓
需要反复 unlock / lock
       ↓
需要 unique_lock
```

## 生产者与等待规则

```cpp
void Producer(int value) {
    {
        std::lock_guard lock(mutex);
        queue.push(value);
    }
    cv.notify_one();
}
```

- 条件变量允许虚假唤醒，因此使用带谓词的 `wait`，醒来后重新检查条件。
- 队列及其条件的读写由同一把 mutex 保护；通知本身不替代状态同步。
- `wait` 原子地释放锁并进入等待；不要用示意中的独立 `unlock()` + `sleep()` 实现它，否则可能丢失唤醒。
- 等待返回时已经重新持锁。通知不代表条件一定仍满足。
- `std::condition_variable` 要求 `std::unique_lock<std::mutex>`；`condition_variable_any` 可支持其他满足要求的锁类型。
